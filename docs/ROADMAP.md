# 路线图

> 这不是排期表，是**决策记录**：说明项目为什么存在、优先做什么、明确不做什么。
> 不做日期承诺；方向变了先改这里，再改代码。

## 一句话定位

把 Claude Code 的扩展机制（rules / hooks / policy / plugins）工程化：
**研究插件是真实用例，文档与参考实现是可复用方法，校验与 CI 保证结论可复跑。**

## 三层结构

| 层 | 资产 | 服务谁 | 判别标准 |
|---|---|---|---|
| **交付层** | 研究专家插件、Slidev / AntV / agent-policy | 想直接用的人 | 能否完成真实任务 |
| **方法层** | `docs/cc-guide`、`.claude/hooks/`、agent-policy 引擎 | 想自己搭扩展的项目 | 能否被别的项目照抄 |
| **质量层** | 校验脚本、CI、尺寸/链接/表格守卫 | 维护者 | 结论能否复跑 |

三层不是并列：**方法层是主产品**，交付层提供真实用例，质量层防止前两层腐化。

## 当前优先级

### P0 · 参考库与引擎的自动验证

- 18 个 hook 脚本按 `examples/*.json` 自动冒烟，断言退出码；
- policy 引擎补边界用例（路径 glob、越界、空 TOML、fail-open/closed）；
- 挂进 CI，参考实现从“能看”变成“被验证”。

### P1 · 在本仓库落地策略

- 补 `permissions.deny` 的工作区边界；
- 建立 `.claude/rules/`（按路径加载的规范）；
- 按需注册 `err-catcher.py`，其余 hooks 继续作为参考。

### P2 · 多宿主导出

只有当**确实需要同时维护第二个宿主**（Cursor / Gemini / Kiro…）时，
再给 agent-policy 加 `export`；否则不提前抽象。

## 明确不做

- 不为 UI 细节做没有请求的打磨；
- 不追求所有易变数字同步——只保留脚本能守护的少数；
- 不把 hooks 参考库迁移成 policy（副作用 ≠ 判定）；
- 不在只有一个宿主时写导出器；
- 不新增没有真实使用场景的插件。

## 完成标准

| 层 | 标准 |
|---|---|
| 交付层 | 每个插件至少有一个真实任务跑通 |
| 方法层 | 每条结论有复跑命令；每个参考脚本有样例输入 |
| 质量层 | CI 覆盖 manifest / 链接 / 表格 / 尺寸 / policy / hooks |

## 何时重审

- 新增或下线一个插件；
- 新增一个 agent 宿主；
- 连续两次改动都落在同一层——说明投入配比需要调整。
