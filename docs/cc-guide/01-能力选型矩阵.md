# 01 · 能力选型矩阵

> **本章要回答的问题**：Claude Code 有十几个扩展层，为什么大多数人的配置都是错的？
> 答案：不是选错了工具，而是**没有区分「确定性约束」和「非确定性引导」**。

---

## 🎯 先记住这一条判据

官方 [best-practices](https://code.claude.com/docs/en/best-practices) 把所有指令机制分成两类：

| 类别 | 机制 | 保证强度 |
|------|------|---------|
| **确定性** | 权限规则、hooks、沙箱 | **不依赖模型配合**，违反就被拦下 |
| **非确定性** | CLAUDE.md、skill、prompt 型 hook | 模型"通常会遵守"，但不保证 |

> **要"不许有例外"的规则，必须用前者。**
> 写进 CLAUDE.md 的「永远不要提交 secrets」是建议；写进 `permissions.deny` 的 `Read(*/secrets/*)` 是事实。

<figure>
  <img src="../assets/fig-determinism.svg" alt="同一规则两种写法的强度对比：写在 CLAUDE.md 里模型只是通常会遵守，写在 permissions.deny 里 Claude Code 直接拦截">
  <figcaption>图 1-1 · 同一条规则，两种写法，保护强度差一个数量级</figcaption>
</figure>

**本仓库实例**：

| 写法 | 位置 | 保护强度 |
|------|------|---------|
| 「遵循 `.gitmessage` 的 Conventional Commits 格式」 | `CLAUDE.md` | 靠模型自觉 |
| `deny: ["Write(.env*)"]` | `.claude/settings.json` | 任何会话、任何模式都写不了 `.env` |

## 📐 12 层能力全景

<figure>
  <img src="../assets/fig-decision.svg" alt="能力选型决策树：从绝对不能违反的规则到跨会话协同，每类问题对应一个首选机制">
  <figcaption>图 1-2 · 能力选型决策树 —— 先问「这条约束需要多强」</figcaption>
</figure>

| 层 | 载体 | 何时加载 | 谁来读 | 确定性 |
|----|------|---------|-------|-------|
| **1. CLAUDE.md** | `CLAUDE.md` / `CLAUDE.local.md` | 启动时（+ 子目录按需） | 模型 | 非确定 |
| **2. AGENTS.md** | `AGENTS.md` | 启动时 | 模型 | 非确定 |
| **3. 路径规则** | `.claude/rules/*.md` | 匹配文件被读/写时 | 模型 | 非确定 |
| **4. Auto memory** | `~/.claude/projects/<p>/memory/` | 启动时（前 200 行 / 25KB） | 模型 | 非确定 |
| **5. Output style** | `output-styles/*.md` | 启动时 | 模型 | 非确定 |
| **6. Skill** | `SKILL.md` | description 常驻；正文调用时 | 模型 | 半确定（`allowed-tools` 是确定的） |
| **7. Subagent** | `agents/*.md` | 委派时 | **独立上下文** | 独立权限 |
| **8. Workflow** | 脚本化流程 | 显式触发 | 多 agent | 独立 |
| **9. 跨会话消息** | socket / SendMessage | 跨会话 | 对方会话 | 独立 |
| **10. MCP** | `.mcp.json` | 工具名常驻 | 模型 | 由权限规则约束 |
| **11. Hook** | `hooks/hooks.json` | 事件触发 | **代码执行** | **确定** |
| **12. Plugin** | `.claude-plugin/plugin.json` | 启用时 | 打包分发 | 取决于内含 |

> 表中 12 层对应官方文档的 11 类扩展点（Plugin 是分发容器，单独计一层更清晰）。

## 🔍 核心判据：skill 还是 subagent？

这是最高频的误判。两个都能"被调用"，但机制完全不同。

| | Skill | Subagent |
|---|-------|----------|
| **上下文** | 与主会话**共享** | **独立**上下文窗口 |
| **产物** | 回到主会话 | 只有摘要 + 元数据回传 |
| **适合** | 需要主会话继续用其上下文 | 大段阅读/检索，结果只需结论 |
| **工具** | `allowed-tools` 授予免批准 | 独立 `tools` / `disallowedTools` |
| **模型** | 可指定 | 可指定（含 `inherit`） |
| **嵌套** | — | 最多 3 层（默认，可用 `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` 调整） |

**一句话判据**：

> 需要**隔离上下文** → subagent；只需要**可复用指令 + 按需加载** → skill。

**本仓库实例**：

`plugins/evolutionary-biology-expert/skills/academic-literature-analysis/SKILL.md` 描述"深度分析文献"，
需要 `article-mcp` 检索 + `sequentialthinking` 推理，但结果（分析报告）要留在主会话继续写 → **skill 正确**。

反例：如果改成 subagent，文献全文会进 subagent 的上下文，报告摘要回到主会话，
主会话再写报告时会丢失原文细节 → 反而更差。

## 🔍 核心判据：CLAUDE.md 还是 skill 还是 rule？

| 场景 | 用什么 | 理由 |
|------|-------|------|
| 每个会话都要知道的（构建命令、目录布局、"always do X"） | CLAUDE.md | 启动即加载 |
| 只在某一类文件上成立的（"API handler 放 `src/api/handlers/`"） | `.claude/rules/` + `paths:` | 按需加载，不占常驻上下文 |
| 多步流程，需要时才做（"怎么写一个插件"） | Skill | description 常驻但不占正文 |
| 每次会话都要跑一遍的（"提交前跑格式化"） | **Hook**（`PostToolUse`） | 确定性，不依赖模型 |

**本仓库实例**：

本仓库 `CLAUDE.md` 当前 **368 行**（官方建议 ≤ 200 行），
含目录结构、配置层次、Git 规范 —— 骨架是合格的，但已经超标 84%。
而"如何新增一个插件"是 6 步流程，按官方建议应当拆成 skill，目前仍留在 CLAUDE.md 里（**待优化项**）。
详见 [02 上下文经济学](02-上下文经济学.md#本仓库的三个具体问题)。

## 🔍 核心判据：hook 还是 prompt？

hooks 的 handler 有 5 种 type，决定权出口完全不同：

| type | 谁做决定 | 确定性 | 适用 |
|------|---------|-------|------|
| `command` | 你的脚本 | **完全确定** | 格式化、校验、拦截 |
| `http` | 你的服务 | 完全确定 | 自建策略服务 |
| `mcp_tool` | MCP 工具 | 取决于工具 | 调用外部决策服务 |
| `prompt` | **另一个模型** | 非确定 | 需要语义判断 |
| `agent` | **另一个模型** | 非确定 | 需要多步推理 |

> `prompt` / `agent` 型 hook 的裁决者是模型 → **不要用来做"绝不允许"的规则**。

**本仓库实例**：
`.claude/hooks/err-catcher.py` 是 `command` 型 —— 匹配错误模式并写入 `docs/error-playbook/`。
这类"确定性分类 + 确定性记录"正是 `command` hook 的正确用途。

> ⚠️ **当前状态**：本仓库 `.claude/settings.json` 的 `"hooks": {}` 为空，
> 18 个 hook 脚本全部未注册（由 commit `fb9f4c3` "禁用所有 hooks 减少噪音" 关闭）。
> 这意味着 `docs/error-playbook/` 目前不会自动积累。
> 详见 [04 权限与护栏](04-权限与护栏.md#PreToolUse-hook-可编程的策略层)。

## 🔍 核心判据：MCP 还是 skill？

| | MCP | Skill |
|---|-----|------|
| 提供什么 | **外部服务的能力**（新工具） | **流程说明**（已有工具的用法） |
| 工具名 | `mcp__<server>__<tool>` | 不产生新工具 |
| 启动开销 | 有（进程/HTTP） | 无 |
| 何时选 | 需要访问 Claude 本身没有的能力 | 需要教 Claude 怎么用已有能力 |

**本仓库实例**：
`.mcp.json` 配了 8 个 server（article-mcp / crawl-mcp / notion / zotero-mcp / zread / zai / web-search-prime / web-reader）。
每个 server 的工具定义都常驻上下文 —— **这是上下文成本的重要来源**，详见 [02 上下文经济学](02-上下文经济学.md)。

`infographic-creation` skill 只教 AntV DSL 语法，不需要新工具 → 用 skill 正确。

## ⚠️ 三个最常见的错误

### 错误 1：把安全规则写进 CLAUDE.md

```markdown
<!-- ❌ 非确定 -->
不要读取 .env 文件
```
```json
<!-- ✅ 确定 -->
{ "permissions": { "deny": ["Read(.env*)"] } }
```

### 错误 2：给 skill 授过宽的 `allowed-tools`

官方原话：*"A skill can grant itself broad tool access, so review the `allowed-tools` of skills checked into a repository before you run Claude Code there."*

`allowed-tools` 的语义是**免批准**，在 skill 被调用的那一轮内生效。
授予 `Bash` 意味着这一轮里 Claude 跑任何命令都不问你。

**本仓库实例**：`plugins/*/skills/*/SKILL.md` 中的 `allowed-tools` 全部包含 `Bash`。
对"读文献→写报告"这类任务，`Read, Write, Edit, Task` 已足够，`Bash` 是可以收窄的。

### 错误 3：用 `deny` 去管 `WebFetch` 的同源绕过

`deny: ["WebFetch(domain:example.com)"]` **管不住** `Bash(curl https://example.com)`。
权限规则是按工具名匹配的，不是按网络目标匹配的。

要真正封禁，需要沙箱（`sandbox` 设置）+ 网络边界，
或用 `PreToolUse` hook 检查完整命令行 → 详见 [04 权限与护栏](04-权限与护栏.md#沙箱-权限之外的第二层)。
