### ⚠️ Claude Code 自己已经报了警

启动日志里这一行不是我们推断的，是它主动说的：

```text
[WARN] Skill listing over budget: 145 skills, 46109 chars > 6000 budget
       — descriptions will be truncated.
       Run /skills to disable some, or raise skillListingBudgetFraction in settings.
```

**"descriptions will be truncated" 的后果**：Claude 只看得到清单的前 6000 字符，
排在后面的 skill 的 `description` 被截掉 → **它不知道那些 skill 存在** → 不会去调用它们。

本机 skill 的来源分布（同样来自 debug 日志）：

```text
Loaded 124 unique skills (124 unconditional, 0 conditional,
                         managed: 0, user: 101, project: 23, additional: 0)
Total plugin skills loaded: 9 (0 duplicate/user-owned entries skipped)
getSkills returning: 124 skill dir commands, 9 plugin skills, 31 bundled skills, 1 builtin plugin skills
Sending 145 skills via attachment (initial)
```

按来源拆开（用 `scripts/measure_context.py` 精确数出**本项目实际生效**的部分）：

| 来源 | 生效/总数 | description 字符数 | 估算 tokens |
|------|---------|------------------|-----------|
| **用户级 `~/.claude/skills/`** | 101/101 | **26,269** | **≈12,090** |
| 项目级 `.claude/skills/` | 22/23 | 1,616 | ≈980 |
| 插件 skill（已启用 9 个） | 9 | 1,141 | ≈360 |
| **skill 小计** | **132** | **29,026** | **≈13,430** |
| 用户级 `~/.claude/agents/` | 8/10 | 2,288 | ≈570 |
| 项目级 `.claude/agents/` | 3/4 | 75 | ≈75 |
| 插件 agent（已启用 4 个） | 4 | 887 | ≈270 |
| **agent 小计** | **15** | **3,250** | **≈920** |
| 已安装但本项目未启用（figma / vercel） | — | 11,960 | ≈2,970 |

> ⚠️ **agent 不进 skill 清单**。agent 的 description 走独立加载路径，
> 不在 `Skill listing over budget` 的统计范围内 —— 所以 46,109 这个数**只含 skill**。
> 同理，figma / vercel 那 11,960 字符因为插件未启用，**也不在** 46,109 里。

**那 46,109 到底是怎么凑出来的**（skill 清单专属）：

| 项 | 字符数 |
|----|-------|
| 本仓库生效的 skill（上表 skill 小计） | 29,026 |
| 其余 skill（内置 / bundled）+ 名称前缀 + 格式化开销 | 17,083 |
| **Claude Code 实测发出**（`Sending 145 skills`） | **46,109** |

> `getSkills` 实际返回 **165** 个（124 skill 目录 + 9 插件 skill + 31 bundled + 1 builtin plugin），
> 发出前按名称去重，最终 `Sending 145 skills`。

> **估算口径**：`scripts/measure_context.py` 按 `CJK 字数 + ASCII 字符数 ÷ 4` 估算。
> 用户级 skill 的 26,269 字符里只有 7,407 是中文，其余 18,862 是英文 ——
> 所以 ≈12,090 tok ≈ 7,407 + 18,862÷4，而不是"2.6 万字 ≈ 1 万 token"。
> Anthropic 的分词器未公开，**量级可靠、个位不可信**。
> **字符数是精确的**（`scripts/measure_context.py` 直接数出来的），token 数是估算。
> 用 `/context` 可以得到 Claude Code 自己的精确数字。

> ⚠️ **四个 frontmatter 解析失败的文件**（`explore/SKILL.md`、
> `python-zen-coding-expert.md`、`story-generator.md`、`dev-planner.md`）
> 会被**静默忽略** —— 它们根本不进上下文，也**不会**被调用。
> 详见 [07 排错手册](07-排错手册.md)。

## ⚠️ 本仓库的三个具体问题

### 问题 1：skill 清单超预算，主因在用户级目录

**101 个用户级 skill 的 description 占了 26,269 字符 —— 是项目级 1,616 字符的 16 倍。**

本仓库只贡献了 22 个能生效的 skill（23 个文件），但清单超预算这件事**主要不是本仓库造成的**。
修本仓库能缓解，但真正的杠杆在 `~/.claude/skills/`（arkcli / lark / gsap 等大集合）。

| 动作 | 效果 |
|------|------|
| `/skills` 停用当前项目用不到的 skill | 直接减少清单长度 |
| 缩短每个 skill 的 `description` | 同上，且不影响 skill 正文 |
| 把 `~/.claude/skills/` 里不常用的挪出目录 | 最彻底 |

### 问题 2：`CLAUDE.md` 超标 104%

官方建议：**每个 CLAUDE.md 控制在 200 行以内**。

本仓库 `CLAUDE.md` 当前 **416 行 / 10,748 字符**（≈4,485 tok）
（2026-10-30 实测快照；本文件改动后行数会漂移，用 `wc -l CLAUDE.md` 复核）。
超出的部分主要是可以按需加载的内容：

| 区块 | 行数 | 建议去处 |
|------|------|---------|
| 本地技能集详解（`/tdd` `/bdd` `/gh` `/sdr` … 13 个） | ~90 | 拆成 `.claude/skills/` 下的 skill |
| `/cleanup` 冗余模式对照表 | ~20 | 拆成 skill 的 `references/` |
| `tmp/` 目录说明 | ~8 | 移到 `docs/` |
| 插件列表（6 个插件 + 版本号） | ~15 | 由 `.claude-plugin/marketplace.json` 生成，或移到 `docs/` |

**可立即做的拆分**：把 13 个本地技能的详细说明从 CLAUDE.md 移到各自的 `SKILL.md`（或 `references/`），
CLAUDE.md 只留一张技能表和触发方式。

### 问题 3：全局 `AGENTS.md` 通过 `@import` 引入

`C:\Users\gqy17\.claude\CLAUDE.md` 第一行是 `@../.codex/AGENTS.md`。
import 机制与 CLAUDE.md **一同加载**，且 **import 不降低上下文成本**（官方原话：
*"Imports help you organize a long file but don't reduce its context cost"*）。

所以全局那份 552 字符的工具清单是**每个会话都付**的。这本身合理，但要知道它不是"免费的分层"。

## 🔄 压缩（compaction）到底保留了什么

上下文接近上限时 Claude Code 自动压缩会话。这不是"截断"，而是**按机制分别处理**：

| 机制 | 压缩后 |
|------|--------|
| 系统提示词、output style | **仍然生效** |
| 项目根 `CLAUDE.md`、无作用域规则 | 从磁盘**重新注入** |
| Auto memory | 从磁盘**重新注入** |
| Skill description | 从当前 skills **重建并重新注入**（需 v2.1.304+） |
| Git status 快照 | 从仓库**重新读取** |
| plan 模式写下的 plan | 从磁盘**重新注入** |
| 带 `paths:` 的规则 | **按需**重新加载 |
| 子目录嵌套 CLAUDE.md | **按需**重新加载 |
| Claude 读/编辑过的文件 | **最多重读 5 个**，按最近修改优先 |
| **已调用的 skill 正文** | 重新注入，但**每个 skill 上限 5,000 tokens、总计 25,000 tokens**，超了**从最旧的开始丢** |
| 后台命令、后台 subagent | **继续运行** |
| hook 此前注入的上下文 | 随对话一起被摘要 |

### 两条立刻可用的推论

**推论 1：把最重要的指令写在 SKILL.md 的最前面。**
截断保留文件开头，所以 skill 的"总纲"必须在顶部，不能把关键约束放在末尾。

**推论 2：想让某条规则跨越压缩存活，就别给它加 `paths:`。**
带 `paths:` 的规则会被当作"路径触发的临时上下文"，压缩时被一起摘要掉。
需要长期生效的规则，要么放项目根 CLAUDE.md，要么不带 `paths:`。

## 🎛️ 手动控制上下文的 5 个手段

| 手段 | 用法 | 何时用 |
|------|------|--------|
| **带焦点的压缩** | `/compact focus on the auth bug fix` | 开始新的大任务前 |
| **局部压缩** | `/rewind` → 选消息 → `Summarize from here` | 只想丢掉某段之前的闲聊 |
| **提前压缩** | `/autocompact 500k` | 想在更早的阈值触发自动压缩 |
| **彻底清空** | `/clear` | **切换到无关任务时**（最有效） |
| **委派大读取** | 把检索/阅读交给 subagent | 只想要结论时 |

> `/clear` 是被严重低估的命令。旧对话会挤掉你接下来需要的文件，且**每条消息都要为它付费**。
> 切换任务就 clear，是最高杠杆的单条操作。

### 委派大读取的具体收益

subagent 在**自己的**上下文窗口里读文件，只有摘要和一小段元数据回到主会话。

**本仓库场景**：分析一个 5,000 行的 Python 文件，
- 直接读 → 主会话 +5,000 tokens，且这些内容会一直留着直到压缩
- 交给 subagent → 主会话只收到 ~500 tokens 的结论

对于本仓库这类"读 15 个 skill 文件 + 6 个 manifest"的任务，这直接决定了会话能不能撑到收尾。

## 🗄️ Prompt caching：什么会让缓存失效

缓存命中意味着**不重复计费**已发送的前缀。官方明确列出了会让缓存失效的操作：

### ❌ 会失效

| 操作 | 说明 |
|------|------|
| 切换模型 | 缓存按模型分桶 |
| 改变 effort level | — |
| 开启 fast mode | — |
| 连接/移除 MCP server | **工具列表变了 → 前缀变了** |
| 启用/禁用插件 | 同上 |
| 拒绝整个工具（deny 整个 tool） | 工具列表变了 |
| 压缩会话 | 对话前缀重写 |
| 累积大量图片 | 多模态块不可复用 |
| 升级 Claude Code | — |

### ✅ 会保留

| 操作 | 说明 |
|------|------|
| 编辑仓库里的文件 | 文件内容不在缓存前缀里 |
| 会话中途编辑 CLAUDE.md | — |
| 改变权限模式 | — |
| 改变 output style | — |
| **调用 skills 和 commands** | — |
| `/recap` | — |
| 回退对话（rewind） | — |

> **本仓库的实际含义**：
> `.claude/settings.json` 里 `enabledPlugins` 的增删、MCP server 的增删，都会**清空整个缓存前缀**。
> 如果你在调试时反复开关插件或改 `.mcp.json`，每次都会重新计费整个前缀。
> **调试期把插件集合固定下来，比反复试更省钱。**

## 🔍 怎么查自己的实际占用

```bash
/context        # 按类别实时分解：哪些 CLAUDE.md、哪些 memory 文件被加载了
/memory         # 打开并编辑 memory 文件
/usage          # 成本与用量
/skill-doctor   # 诊断 skill 配置问题
```

`/context` 会明确列出**加载了哪些 CLAUDE.md 和 auto memory 文件** —— 这是验证"我的规则到底生效没有"的唯一直接手段。
