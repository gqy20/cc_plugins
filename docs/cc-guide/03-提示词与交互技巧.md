# 03 · 提示词与交互技巧

> **本章要回答的问题**：同样的模型，为什么有人效率是别人的三倍？
> 答案：**提示词的写法决定了 agentic loop 的收敛速度**，而不是措辞本身。

---

## 🧠 先理解 agentic loop

Claude Code 的工作方式是三段循环：**收集上下文 → 采取行动 → 验证结果**，反复直到任务完成。

| 阶段 | Claude 在做什么 | 出口 |
|------|----------------|------|
| ① 收集上下文 | 读文件、搜代码、查文档 | 拿到对现状的判断 |
| ② 采取行动 | 编辑文件、运行命令、调用工具 | 世界被改变 |
| ③ 验证结果 | 跑测试、看报错、确认 | 通过 → 结束；不通过 → 回到 ① |

> 任何一步都可以**打断**：按 `Esc` 取消当前轮。
> 想让新指令**排队**而不是打断，用 `Ctrl+X Enter` —— 见[消息队列](#消息队列-不要打断-用-Ctrl-X-Enter-排队)。

  <figcaption>图 3-1 · 三段循环与提示词的收敛速度</figcaption>

**关键推论**：提示词的作用不是"告诉 Claude 怎么做"，而是**减少它在循环里瞎转的次数**。
一个模糊的提示词会让循环多跑 3-5 轮（每轮都贵），一个精确的提示词 1-2 轮就收敛。

官方 best-practices 的原话是 **"Delegate, don't dictate"**（委派，不要指挥）：
给出**目标 + 约束 + 验收标准**，而不是逐步指令。

## ✍️ 提示词配方

### 配方 A：给目标 + 约束 + 验收标准

```markdown
❌ 「帮我优化一下这个插件的加载速度」

✅ 「plugins/infographic-viz 的 skill 在启动时被完整加载，
    但它的正文只有调用时才需要。
    目标：减少启动时的上下文占用。
    约束：不能改变用户可见的命令名。
    验收：claude plugin validate 仍然通过，且 /context 里
    启动开销下降。
    动手前先告诉我你打算改哪几处。」
```

三要素各自的作用：

| 要素 | 作用 | 缺失后果 |
|------|------|---------|
| **目标** | 定义"完成"是什么 | Claude 猜，可能做完不对的东西 |
| **约束** | 划出不能碰的边界 | Claude 顺手"优化"了你不想动的地方 |
| **验收** | 给出可判定的完成标志 | Claude 自认为完成了，实际没验证 |

### 配方 B：诊断类问题——先要证据再要结论

```markdown
「`claude plugin validate` 报 "skills entries must be directories
containing SKILL.md"。
先读 plugins/slidev-generator/.claude-plugin/plugin.json 和
plugins/slidev-generator/skills/ 目录结构，
告诉我根因和最小修复方案，先不要改文件。」
```

这个配方把「调查」和「执行」分开，避免 Claude 在信息不足时就开始改。

### 配方 C：让 Claude 自己校验

```markdown
「按下面的规范重写这 6 个 skill 的 frontmatter：
  - name 用 kebab-case，与目录名一致
  - description 中文，包含触发场景
  - allowed-tools 保留原有
改完后逐个跑 claude plugin validate，把输出贴给我。」
```

"改完后验证并贴输出"这句把验证变成了**流程的一部分**，而不是可选的后续步骤。

## 🎭 输出风格（Output Style）

输出风格是**整个会话**生效的指令。一个会话只能有一个。

| 风格 | 改变什么 | 什么时候用 |
|------|---------|-----------|
| **Default** | 不加风格指令，走标准软件工程系统提示词 | 默认 |
| **Proactive** | 直接开始做，对常规决策做合理假设而不停下问 | 你想让它一路做到底，你来纠偏 |
| **Concise** | 首句给结果，省掉铺垫、叙述和总结 | 觉得默认太啰嗦（需 v2.1.237+） |
| **Explanatory** | 在代码旁加 `Insight` 块解释选择理由 | 学习代码库时 |
| **Learning** | 解释思路，**留小段代码让你自己写** | 练习时 |

### 风格 vs 其他机制

这是官方给出的对照表，值得整表记住：

| 你想要 | 用什么 | 为什么 |
|--------|-------|-------|
| 每次回答都某种语气/长度/格式 | **output style** | 整个会话生效，一条命令切换 |
| Claude 知道项目约定、命令、结构 | **CLAUDE.md** | 换风格也一直在 |
| 某一类任务的指令（发版清单、评审流程） | **skill** | 只在调用/匹配时加载，不影响其他回答 |
| **每次都必须发生**（每次编辑后格式化、拦截某命令） | **hook** | Claude Code 自己执行，不依赖模型 |
| 一个有独立指令/模型/工具的助手 | **subagent** | 独立上下文，返回摘要 |

### 两个必须知道的副作用

1. **output style 是非确定性的** —— 它只是给模型的指令，模型可能不遵守。要"绝不允许"就用 hook。
2. **自定义 style 默认会丢掉 Claude Code 内置的软件工程指令**（如何限定改动范围、如何写注释、如何验证工作）。
   要保留就设 `keep-coding-instructions: true`；但这只在**完整系统提示词**下生效，
   需要同时设 `CLAUDE_CODE_SIMPLE_SYSTEM_PROMPT=0`。

> **本仓库现状**：`.claude/settings.json` 未设 `outputStyle`，走默认。
> 考虑到本项目是"研究分析 + 插件开发"混合场景，`Concise` 或 `Proactive` 都值得试一次。

## ⌨️ 交互技巧速查

### `!` 前缀 = 直接跑 shell，不经 Claude

```bash
! npm test
! git status
! ls -la
```

| 特性 | 说明 |
|------|------|
| 输出**加入对话上下文** | 之后 Claude 能直接解释这些输出 |
| **不需要 Claude 批准** | 你自己输的，权限系统不管 |
| 支持 `Ctrl+B` 后台化 | 长命令不阻塞 |
| 支持 Tab 补全 | 历史命令 + 实时路径补全（Windows 也用 `/` 触发） |
| **在沙箱外运行** | ⚠️ 沙箱只作用于 Claude 运行的命令，**你手输的 `!` 不受限** |

> ⚠️ 最后一条是本章最重要的安全提示：即使你配了沙箱，`! curl ...` 依然在沙箱外执行。

想避免 Claude 对 shell 输出也做回应（省 tokens），设 `respondToBashCommands: false`。

### 消息队列：不要打断，用 `Ctrl+X Enter` 排队

Claude 工作时你打字按 `Ctrl+X Enter`，消息会**排队**而不是打断当前轮次。
**排队中的消息显示为灰色**，直到 Claude 真正开始回应它 —— 所以你能一眼看出哪些还没被处理。

| 想要的效果 | 按什么 | 底层动作 |
|-----------|--------|---------|
| **排队**，等当前轮结束再发，**绝不打断** | **`Ctrl+X Enter`** | `chat:queueSubmit` |
| **立刻发出去**，不等当前轮 | **`Enter`** | `chat:submit` |
| 把**已经排队的**消息立刻发出去 | **`Ctrl+Enter`** 或 **`Ctrl+X Ctrl+S`** | `chat:sendNow` |
| **取回**排队的消息重新编辑 | 输入框为空时按 **`Up`** | `history:previous` |
| **打断**当前轮（不提交草稿），已排队消息立刻发出 | **`Esc`** | `chat:cancel` |

> ⚠️ 官方 interactive-mode 页在这里已经过时（说 Enter 会排队），排队键其实是 `Ctrl+X Enter`。详见 [07 坑 6](07-排错手册.md)。

> ⚠️ `Ctrl+Enter` 在**不报告扩展键**的终端里会退化成普通 `Enter`（就变成立即发送）。
> 这种终端用 `Ctrl+X Ctrl+S` —— 它在**任何终端**都有效。

**`Ctrl+X` 是和弦（chord）前缀**：`Chat` 上下文占用 `ctrl+x` 前缀的默认和弦有 6 个：

```text
ctrl+x ctrl+k   停止本会话所有后台 subagent
ctrl+x ctrl+e   用外部编辑器写提示词
ctrl+x enter    排队发送        ← 本节的主角
ctrl+x ctrl+a   折叠/展开提示框上方的横条
ctrl+x ctrl+s   立刻发出已排队消息
ctrl+x tab      聚焦提示框上方的横条
```

> **想自己验证键位？** 二进制里就有出厂默认值，不用猜：
> ```bash
> uv run python scripts/extract_keybindings.py --context Chat
> ```
> 会话里按 `?` 也能看当前可用的快捷键。

**不同内容的送达时机不一样**：

| 排队内容 | 何时送达 |
|---------|---------|
| 普通消息 | 当前工具调用结束就送出（**同一轮内**）；轮次自然结束才发出去的话，**不需要再按一次键** |
| 命令 / `!` shell 命令 | 轮次**完全结束**后，按你排队的顺序**逐个执行** |

**`Ctrl+Enter`（`chat:sendNow`）在不同状态下行为不同**：

| Claude 正在做什么 | `Ctrl+Enter` 的效果 |
|-----------------|-------------------|
| 跑 shell 命令 / subagent / 其他**能转后台**的活 | 那些活**转到后台继续跑**，消息在同一轮里送进去 |
| 只是在写回复，或在跑**不能转后台**的活 | **打断当前轮**，消息下一轮送出（v2.1.281 起才有这个区分） |
| 你排队了一个 `!` shell 命令在前面 | **直接打断当前轮** |
| 你在 shell 模式（`!` 前缀） | 只是排队这条命令 |
| 什么都没在跑 | 就是普通提交 |

**有些命令不排队，发送即执行**：`/model`、`/effort`、`/fast` —— 三个都是改设置。

> 实践建议：Claude 正在跑长任务时，**不要按 `Enter` 也不要按 `Ctrl+C`**，
> 把补充要求用 `Ctrl+X Enter` 排队即可。
> 中断会丢掉已完成的推理，且重新开始要重读上下文。

### 后台化与批量停止

| 快捷键 | 作用 | 底层动作 |
|-------|------|---------|
| `Ctrl+B` / `Ctrl+X Ctrl+B` | 把当前前台任务移到后台（tmux 用户按两次） | `task:background` |
| `Ctrl+X Ctrl+K` | 见上文和弦表 | `chat:killAgents` |
| `Ctrl+L` / `Cmd+K` | 重绘屏幕，**保留**输入与对话（显示错乱时用） | `chat:clearInput` / `chat:clearScreen` |
| `Ctrl+G` | 用默认编辑器写提示词 | `chat:externalEditor` |
| `Ctrl+J` | 插入换行而不提交 | `chat:newline` |
| `Ctrl+S` | 暂存（stash）当前提示词 | `chat:stash` |
| `Shift+Tab` | 循环切换权限模式 | `chat:cycleMode` |
| `Alt+P` / `Alt+O` / `Alt+T` | 模型选择器 / 快速模式 / 扩展思考 | `chat:modelPicker` / `fastMode` / `thinkingToggle` |
| `Ctrl+R` | 搜索历史命令 | `history:search` |
| `Ctrl+T` / `Ctrl+O` | 显示待办清单 / 详细 transcript | `app:toggleTodos` / `app:toggleTranscript` |
| `Ctrl+D` | 退出（800ms 内按第二次）；有文本时是删字符 | `app:exit` |
| `Ctrl+C` | 中断运行；空闲时第一次清输入、第二次退出 | `app:interrupt` |

> `Ctrl+X Ctrl+K` 很实用：派了 5 个 subagent 后想全部收手，一条命令搞定。

### 改键位：`~/.claude/keybindings.json`

会话里执行 `/keybindings` 会创建这个文件，**改完自动生效，不用重启**。

```json
{
  "$schema": "https://www.schemastore.org/claude-code-keybindings.json",
  "bindings": [
    {
      "context": "Chat",
      "bindings": {
        "ctrl+q": "chat:queueSubmit",
        "ctrl+x tab": null,
        "ctrl+x enter": null,
        "ctrl+x ctrl+a": null,
        "ctrl+x ctrl+e": null,
        "ctrl+x ctrl+k": null,
        "ctrl+x ctrl+s": null
      }
    }
  ]
}
```

> 上例把 `Ctrl+X` 前缀下的 **6 个和弦全部解绑**，才能把 `Ctrl+X` 独占成一个新前缀。
> 只解绑其中一个没用 —— 其余 5 个仍会先命中和弦表。
> 这 6 个和弦的出厂绑定见上文 [和弦表](#消息队列-不要打断-用-Ctrl-X-Enter-排队)，
> 也可以用 `scripts/extract_keybindings.py --context Chat` 直接从二进制里读出来。

| 规则 | 说明 |
|------|------|
| 按 **context** 分块 | `Chat` / `Global` / `Task` / `Footer` / `Select` … 每个上下文的键位互不干扰 |
| 值设 `null` = **解绑**默认键 | 想彻底占用 `ctrl+x` 前缀，得把该前缀下所有和弦都解绑 |
| 键名用 `+` 分隔修饰键 | `ctrl+k`、`shift+tab`、`meta+p`；`meta` 在 Windows/Linux 上 = `Alt` |
| 和弦用**空格**分隔 | `ctrl+x ctrl+s` = 先按 `Ctrl+X` 松开，再按 `Ctrl+S`，**间隔不超过 3 秒** |
| 拼错不会报错 | 未知动作名会被**静默跳过**，默认绑定继续生效；用 `--debug` 才看得到警告 |

**不可改的保留键**：`Ctrl+C`（中断）、`Ctrl+D`（退出）、`Ctrl+M`（永远当 Enter）、
`Ctrl+I`（永远当 Tab）、`Ctrl+[`（永远当 Esc）、`Ctrl+H`（退格字节）、Caps Lock。

> **踩坑提示**：Windows Terminal 里 `Ctrl+X` 是 Emacs 风格前缀，可能被终端自身吃掉。
> 如果 `Ctrl+X Enter` 没反应，就把 `chat:queueSubmit` 改绑到 `ctrl+q` 之类的普通组合键。

### `@` 引用文件

`@path/to/file` 直接把文件内容带进上下文。

> 注意：默认 `@` 会带上文件内容。要只带路径不带内容，设 `CLAUDE_CODE_DISABLE_FILE_MENTIONS=1`。

## 🧭 plan 模式：先设计再动手

```bash
claude --permission-mode plan
```

进入后状态栏显示 `⏸ plan mode on`，**批准前不落盘**。适合：
- 改动范围不确定
- 涉及多文件重构
- 想先看方案再决定

plan 模式写下的 plan 会在压缩后**从磁盘重新注入**，不会丢。

## 🧵 并行：用 worktree 而不是切分支

在同一个仓库里同时跑多个会话，用 worktree 隔离工作目录：

```bash
claude --worktree          # 在独立 worktree 中启动
```

Claude Code 也支持 `WorktreeCreate` / `WorktreeRemove` hook 接管创建流程，
以及用 `isolation: worktree` 让 **subagent 各自拥有独立工作区**。

> **本仓库场景**：本项目有 4 个研究插件和 6 个插件包。
> 如果要同时给多个插件补 frontmatter，用 worktree 并行比串行改省时间。

## 📋 可复用的提示词模板

| 场景 | 模板 |
|------|------|
| 理解陌生代码 | 「先不要改任何文件。读 `X` 目录下的文件，画出模块依赖关系，列出我应该先读的 3 个文件及原因。」 |
| 修 bug | 「复现 `X` 的失败。先跑测试确认失败，定位根因，再提出修复方案 —— 方案我确认后才动手。」 |
| 重构 | 「重构 `X`，约束：不改公开 API、不加依赖、每步可回滚。完成后跑 `Y` 验证。」 |
| 写测试 | 「为 `X` 写测试，覆盖 `A/B/C` 三种边界。先列出你打算测什么，我确认后再写。」 |
| 开 PR | 「基于当前分支生成 PR：标题用 Conventional Commits，正文写清动机、变更、影响面。」 |
| 审查 | 「审查 `X` 的改动。重点找：并发问题、错误处理缺失、破坏性变更。按严重度排序。」 |
