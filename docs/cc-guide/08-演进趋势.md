# 08 · 演进趋势

> **本章要回答的问题**：Claude Code 下一步会往哪走？
>
> 答案不靠猜。官方仓库的 `CHANGELOG.md` 逐版本记录了每一次改动 —— **433 个版本、8,442 条变更条目**，
> 覆盖 2025-03 至 2026-10 共 20 个月。把它们按主题归拢，会看到 **8 条方向高度一致的演进主线**。
>
> 技术选型时真正该看的不是「现在有什么」，而是 **哪条线还在加速**。

## 主线 1 · 权限模型：从「问不问」变成「谁来判」

### 现象

早期的权限模型只有一个问题：**这条命令要不要弹窗给你点 allow？**
到 2026 年，问题变成了 **谁来替人做这个决定**，而且判权方被拆成了三层：

```
用户点 allow
    ↓
权限规则（permissions.deny 等）
    ↓
auto 模式分类器（模型判定）
    ↓
企业 managed settings（管理员兜底）
```

### 证据

| 版本 | 变更条目 | 意味着什么 |
|---|---|---|
| `v2.0.68`（2025-12-12） | `Add support for enterprise managed settings. Contact your Anthropic account team to enable this feature.` | 判权权开始向上收 —— 管理员可以覆盖用户 |
| `v2.1.51`（2026-02-23） | `Managed settings can now be set via macOS plist or Windows Registry.` | managed settings 有了 OS 级落地点，不再只是服务器配置 |
| `v2.1.118`（2026-04-22） | `Auto mode: include `"$defaults"` in `autoMode.allow`, `autoMode.soft_deny`, or `autoMode.environment` to add custom rules alongside the built-in list instead of replacing it` | auto 模式有了**自己的规则命名空间**：`autoMode.allow` / `autoMode.soft_deny` / `autoMode.environment` |
| `v2.1.136`（2026-05-08） | `Added `settings.autoMode.hard_deny` for auto mode classifier rules that block unconditionally regardless of user intent or allow exceptions` | 出现了**无条件否决**的分类器规则档位 |
| `v2.1.193`（2026-06-25） | `Added `autoMode.classifyAllShell` setting to route all Bash/PowerShell commands through the auto-mode classifier instead of only arbitrary-code-execution patterns` | 分类器的适用范围可调 —— 从"只查可疑命令"扩到"全查" |
| `v2.1.111`（2026-04-16） | `Auto mode no longer requires `--enable-auto-mode`` | auto 模式去掉实验开关，转正 |
| `v2.1.284`（2026-09-28） | `Changed interactive terminal and VS Code sessions to start in auto mode when no permission mode is configured, on every plan and provider; `permissions.defaultMode` still overrides it` | **auto 模式成了默认值** —— 没配权限模式就自动进 auto mode |
| `v2.1.302`（2026-10-16） | `Added `CLAUDE_CODE_AUTO_MODE_MODEL` to choose the model the client-side auto mode classifier uses` | 分类器本身变成**可替换的模型** —— 判权成了可配置资源 |
| `v2.1.304`（2026-10-19） | `Added `/auto-mode-setup`: a guided setup that reads your project and recent sessions to teach auto mode about your environment` | auto 模式有了**教学流程**，从"通用规则"变成"懂你项目的规则" |
| `v2.1.314`（2026-10-30） | `Added `permissions.blockWritesOutsideWorkingDirectories`: Write, Edit and NotebookEdit refuse paths outside the working directories in every permission mode` | 权限规则第一次做到"**所有模式下都生效**"，与 deny 同级 |

### 对使用者的含义

1. **「问一下」正在变成「问一下谁」**。auto 模式把 59.5% 的 `Fixed` 变成了"分类器误判的修复"，说明分类器本身还在快速迭代 —— 现在依赖 auto 模式，等于依赖一块还在动的地基。
2. **auto 模式已经是默认值了**（`v2.1.284`，2026-09-28）：没显式配权限模式就自动进 auto mode。
   **"点 allow"这个动作正在从默认路径上消失** —— 这不是小事，它意味着默认安全姿态在 2026-09 发生了一次静默切换。
3. **`managed settings` 是新的最高优先级**。它能在服务器端下发（`v2.1.314` 修的正是"远端 managed settings 过期后会静默无策略启动"），意味着 **企业环境下你的 `settings.json` 不是最终说了算的那一层**。
4. **`blockWritesOutsideWorkingDirectories`（v2.1.314）是一个新语义**：它不是"规则"，是"边界"。与 `permissions.deny` 一样在所有权限模式下生效，包括 `bypassPermissions`。

### 🎯 给本仓库的行动项

- 本仓库必须显式写 `"permissions": {"defaultMode": "manual"}`（理由见 [04 · P0′](04-权限与护栏.md)）。
- 本仓库 `permissions.deny` 目前只有 3 条（`Bash(sudo:*)` / `Read(*/secrets/*)` / `Edit(.env*)`），
  **缺 `blockWritesOutsideWorkingDirectories` 这一层边界**。建议补上，并同时补
  `blockReadsOutsideWorkingDirectories` —— 这两条在所有模式下都拦得住，且不依赖模型。
- **注意本仓库的三档模型全部指向 `glm-4.7`（模型网关）**，**auto 模式在本仓库不可依赖**，
  `permissions.deny` 与工作目录边界才是唯一确定性的层（原因见 04 章 P0′）。
  这不是配置问题，是选型结论：**本仓库的权限设计要按"没有 auto 模式"来做**。
- `permissions.allow` 里有一条裸 `"Bash"`（无参数），语义是放行任意 Bash 命令。
  在**原生 Windows、无沙箱**的组合下（见主线 2），这是当前最大的敞口 —— 收窄方案见 [04 权限与护栏](04-权限与护栏.md)。

## 主线 2 · 护栏：从提示层下沉到执行层

### 现象

护栏的重心从"写在 CLAUDE.md 里求模型遵守"，逐步下沉到 **操作系统和 Claude Code 自身强制执行**：

| 层 | 机制 | 强度 |
|---|---|---|
| 提示层 | CLAUDE.md / skill 里的自然语言约束 | 模型"通常"遵守 |
| 决策层 | `permissions.deny` / `PreToolUse` hook 的 `permissionDecision` | Claude Code 强制 |
| 执行层 | **sandbox**（操作系统强制） | 内核强制 |

### 证据

| 版本 | 变更条目 | 意味着什么 |
|---|---|---|
| `v1.0.38`（2025-06-30） | `Released hooks.` | 策略层第一次有了可编程入口 |
| `v1.0.59`（2025-07-23） | `Hooks: Exposed PermissionDecision to hooks (including "ask")` | hook 不只是"观察"，可以**回一个判定** |
| `v2.0.24`（2025-10-20） | `Sandbox: Releasing a sandbox mode for the BashTool on Linux & Mac` | 护栏进入**执行层** |
| `v2.0.30`（2025-10-30） | `Added `allowUnsandboxedCommands` sandbox setting to disable the dangerouslyDisableSandbox escape hatch at policy level` | 连"绕过沙箱"这个逃生舱都可以被**策略层关掉** |
| `v2.1.85`（2026-03-26） | `PreToolUse hooks can now satisfy `AskUserQuestion` by returning `updatedInput` alongside `permissionDecision: "allow"`, enabling headless integrations that collect answers via their own UI` | hook 能**代替人回答**审批问题 |
| `v2.1.101`（2026-04-10） | `Fixed `permissions.deny` rules not overriding a PreToolUse hook's `permissionDecision: "ask"`` | 确立了 **`deny` > hook > 提示** 的优先级 |
| `v2.1.133`（2026-05-07） | `Added `sandbox.bwrapPath` and `sandbox.socatPath` managed settings (Linux/WSL) to specify custom bubblewrap and socat binary locations` | 沙箱的二进制路径本身也可被策略接管（注意标注 **Linux/WSL**） |
| `v2.1.265`（2026-09-08） | `Windows: Fixed Read, Write and Edit refusing every file ("symlink resolution changed after permission was checked") when running inside an AppContainer or restricted-token sandbox` | Windows 上出现的是**系统级 AppContainer / restricted-token**，不是 Claude Code 自己的沙箱 |
| `v2.1.314`（2026-10-30） | `Fixed sandbox protections not applying to a worktree entered by `claude -p --resume` or `--continue`` | 沙箱边界本身仍在被各种入口绕过 —— **这层还没做完** |

**Windows 上没有沙箱，这是官方文档的原话**：

> The sandbox runs on macOS, Linux, and WSL2. **On native Windows, Claude Code runs commands unsandboxed.**
> To use the sandbox on a Windows machine, run Claude Code inside a WSL2 distribution.
> （[官方文档 · sandboxing](https://code.claude.com/docs/en/sandboxing)）

同页还有一句更狠的：设置了 `failIfUnavailable` 时，**在原生 Windows 上 Claude Code 会在启动时直接退出**。
CHANGELOG 里 `v2.1.173`（2026-06-11）修的 `Fixed a spurious "sandbox dependencies missing" startup warning on Windows when sandbox was enabled in settings`
和 `v2.1.299`（2026-10-14）修的 `Fixed sandboxed commands failing on WSL2 with bwrap: Can't mkdir /mnt/c/Program Files/ClaudeCode`
都指向同一结论：**Windows 想有沙箱，只能进 WSL2**。

### 对使用者的含义

1. **`permissionDecision` 让 hook 从"日志"升级为"策略"**。但 v2.1.101 的修复同时说明了一个优先级陷阱：
   **hook 只能把 `deny` 降级成 `ask`，不能把 `deny` 变成 `allow`** —— 写 hook 时不要以为能"放行一切"。
2. **沙箱是执行层，但只在 macOS / Linux / WSL2 上存在**。原生 Windows 上，执行层是空的，
   你的全部防线只剩 `permissions.deny` + hook。
3. **沙箱这层到 2026-10 仍在漏**（v2.1.314 的 worktree 绕过）。它是"当前最强"，不是"已经完备"。

### 🎯 给本仓库的行动项

- hooks 全部未注册（commit `fb9f4c3` 主动关闭），分级放开方案见 [04 权限与护栏](04-权限与护栏.md)。
- **原生 Windows = 无沙箱**，`permissions.deny` 必须自己补齐 Windows 特有敞口；
  WSL2 / 容器的选型见 [04 权限与护栏](04-权限与护栏.md)。

## 主线 3 · 可编程性：从「写提示词」到「写程序」

### 现象

扩展点按时间顺序出现，每一层都比上一层更"可编程"：

| 时间 | 版本 | 扩展点 | 能力 |
|---|---|---|---|
| 2025-06-30 | `v1.0.38` | **Hooks** | 可执行脚本，能观察和裁决 |
| 2025-07-24 | `v1.0.60` | **自定义 Subagents** | 独立上下文的专用执行体（subagent 概念更早：`v1.0.41` 已拆出 `SubagentStop` hook） |
| 2025-10-09 | `v2.0.12` | **Plugins** | 把上面这些打包分发 |
| 2025-10-16 | `v2.0.20` | **Skills** | 可复用的流程说明 + 渐进加载 |
| 2026-02-06 | `v2.1.33` | `TeammateIdle` / `TaskCompleted` hook | hook 事件开始覆盖**多 agent 生命周期** |
| 2026-10-01 | `v2.1.287` | **Claude Mods** | 插件可以改**更深层的行为** |

### 证据

| 版本 | 变更条目 |
|---|---|
| `v1.0.60` | `You can now create custom subagents for specialized tasks! Run /agents to get started` |
| `v2.0.12` | `**Plugin System Released**: Extend Claude Code with custom commands, agents, hooks, and MCP servers from marketplaces` |
| `v2.0.20` | `Added support for Claude Skills` |
| `v2.1.287` | `Added Claude Mods: plugins may now modify deeper behavior` |
| `v2.1.288` | `Added `$.ui.selection()` for mods: returns the text you last selected in fullscreen mode` |
| `v2.1.292` | `Added prompt caching to `$.model.complete` for mods` |
| `v2.1.304` | `Changed mods' `settings.read` hooks to receive each settings layer and rewrite the merged settings, so a managed mod can make an organization's setting a ceiling` |

### 对使用者的含义

**扩展点的"天花板"还在往天上抬。**
从 `v1.0.38` 的 hook（只能执行脚本）到 `v2.1.287` 的 mods（能改 UI、能改模型请求、能重写合并后的 settings），
**两年半里"插件"这个词的含义扩大了至少三倍**。

关键的一条是 `v2.1.304`：mods 的 `settings.read` hook 能**改写合并后的配置**，
让一个 managed mod 把组织级设置变成"天花板"。
**这意味着插件从"加功能"进化到了"改规则"** —— 生态的安全模型随之改变：
以后装一个插件，等于交出一部分策略控制权。

### 🎯 给本仓库的行动项

- 本仓库现在有 **23 个项目级 skill 目录（22 个能生效）+ 4 个项目级 agent + 6 个插件（15 skill / 5 agent）**。
  其中 `taste-analyzer`（Python 代码品位分析）、`design-scout`（设计灵感侦察）这类**与本仓库主题无关**的 skill，
  建议移到用户级或加 `disable-model-invocation: true` —— 它们现在在**每个会话启动时都付费**（见主线 5）。
- **Mods 是本仓库最该跟的新机制**：本仓库的产物就是"插件集合"，
  而 mods 让插件能改 UI 和工具调用规则 —— 意味着 `cc_plugins` 的下一步形态可能是
  **一个 mod**（比如"插件体检"面板），而不只是一个 marketplace。
  建议先用 `claude plugin validate` 把现有 6 个插件的 manifest 全部规范化（`skills` 指目录、`commands` 指文件），
  等 mods 生态成熟时迁移成本最低。

## 主线 4 · 从「一个会话」到「多个并行实体」

### 现象

Claude Code 里"一个会话"的含义被拆开了 —— 现在有 5 种并行实体，各有各的"身份边界"：

| 实体 | 边界在哪 | 何时出现 |
|---|---|---|
| Subagent | 独立上下文，结果回主会话 | `v1.0.60`（2025-07-24，自定义 subagent 可创建） |
| Fork | 从某个点分叉的子上下文 | `v2.1.0`（2026-01-07） |
| Agent Team | 每个成员一个独立 tmux 会话 | `v2.1.32`（2026-02-05） |
| Worktree | 独立 git 工作目录 | `v2.1.49`（2026-02-19） |
| 跨会话消息 | 跨机器、跨进程的会话 | `v2.1.224`（2026-08-07） |

### 证据

| 版本 | 变更条目 | 意味着什么 |
|---|---|---|
| `v2.1.0` | `Added support for running skills and slash commands in a forked sub-agent context using `context: fork` in skill frontmatter` | skill 自己可以声明"在 fork 上下文里跑" |
| `v2.1.32` | `Added research preview agent teams feature for multi-agent collaboration (token-intensive feature, requires setting CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1)` | **多个真正独立的 Claude 实例** |
| `v2.1.49` | `Added `--worktree` (`-w`) flag to start Claude in an isolated git worktree` + `Subagents support `isolation: "worktree"`` | 并行不再靠"别冲突"，而是**靠文件系统隔离** |
| `v2.1.224` | `Added cross-session `SendMessage`: Claude Code sessions can now message each other, on any of your machines, with `ListAgents` to discover them (macOS and Linux)` | 会话获得了**寻址能力**（`ListAgents` / `SendMessage`） |
| `v2.1.239` | `Windows: cross-session messaging is now available, so Claude Code sessions across your machines can message each other with `SendMessage` and find each other with `ListAgents`, as on macOS and Linux` | 补齐 Windows |
| `v2.1.302` | `Changed fork subagents (`subagent_type: "fork"`) to be on by default in `claude -p`, the Agent SDK, the desktop app and VS Code` | fork 从可选变成**默认行为** |
| `v2.1.309` | `Fixed split-pane agent teammates not inheriting the tool deny and `--tools` rules given on the leader's command line` | 多 agent 的**权限继承**仍在补 —— 这层还不成熟 |

### 对使用者的含义

1. **并行能力已经越过"可用"进入"默认"**。fork subagent 在 SDK / 桌面端 / VS Code 里默认开启（v2.1.302）。
2. **`ListAgents` + `SendMessage` 让会话变成了可寻址的实体**（v2.1.239）。
   一个 Claude Code 实例现在可以给另一个实例发消息 —— 这在架构上已经是分布式系统的形状了。
3. **但权限继承、状态持久化这类"多 agent 运维"问题还在持续修**（v2.1.309、v2.1.311）。
   **不要把 agent teams 当成熟产品用**，当实验特性用。

### 🎯 给本仓库的行动项

- 本仓库 `.claude/settings.json` 已设 `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`，
  但 **`.claude/agents/` 只有 4 个本地 agent，且没有一个声明 `isolation: "worktree"`**。
  本仓库是"6 个插件 / 15 个 skill / 5 个 agent"的批量维护型仓库 —— **批量改插件 frontmatter 正是并行收益最大的场景**：
  建议给 `.claude/agents/` 里的插件审查类 agent 加上 `isolation: "worktree"`，
  让"审 6 个插件"这种任务真正并行且互不冲突。
- **注意 v2.1.309 的坑**：team member 的权限规则要显式继承 leader 的 `deny` 和 `--tools`。
  本仓库如果用 agent teams 做批量审查，**必须把 `permissions.deny` 显式传给每个 teammate**，
  否则会出现"某个 teammate 手里没有 deny 规则"的窗口。
- 跨会话消息（v2.1.224）在本仓库的价值有限（CI 为主、单机为辅），**暂不投入**。

## 主线 5 · 上下文：从「一个窗口」到「分层预算」

### 现象

上下文不再是"一个窗口装满为止"，而是**分层预算**：
常驻层（CLAUDE.md + skill 清单）→ 按需层（skill 正文、agent 定义）→ 临时层（对话）→ 压缩层（compaction）。

### 证据

| 版本 | 变更条目 | 意味着什么 |
|---|---|---|
| `v0.2.47`（2025-03-18） | `Automatic conversation compaction for infinite conversation length (toggle with /config)` | 压缩从第一天就有，但只是"别炸掉" |
| `v1.0.86`（2025-08-20） | `Added /context to help users self-serve debug context issues` | 有了**自省工具** |
| `v2.0.74`（2025-12-19） | `Improved `/context` command visualization with grouped skills and agents by source, slash commands, and sorted token count` | `/context` 开始**按来源分组** —— 上下文被正式当成预算来管 |
| `v2.1.243`（2026-08-24） | `Added `promptCacheTtl` and `subagentPromptCacheTtl` settings so API-key and cloud-provider users can keep a 1-hour prompt cache on the main conversation while subagents s...` | 缓存 TTL 变成**可按层配置** |
| `v2.1.248`（2026-08-27） | `Added `experimental.cacheTtl` (`"5m"` or `"1h"`) to agent frontmatter: a per-agent prompt cache TTL used when no subagent TTL setting is configured` | 缓存 TTL 下沉到 **agent frontmatter** —— 每个 agent 独立预算 |
| `v2.1.299`（2026-10-14） | `Added `/usage` warnings for max effort, workflows, always-on context and large tool results` | 出现了 **"always-on context"** 这个概念，并被单独告警 |
| `v2.1.314`（2026-10-30） | `Added idle compaction to VS Code and Claude Desktop's Code tab: a 200K+ token conversation left idle is summarized, and the summary is used on your next message if the prompt cache has expired` | 压缩从"对话太长时"变成**空闲时自动** |

### 对使用者的含义

1. **`always-on context` 被官方正式命名为一个成本项**（v2.1.299）——
   这正是本仓库第 02 章量化的那件事（145 个 skill 的 description 共 46,109 字符 vs 6,000 字符预算）。
2. **预算现在可以分层配**：主会话 1 小时缓存、subagent 另配（v2.1.243 / v2.1.248）。
   换句话说，**"贵的部分放主会话，便宜的部分放 subagent" 已经是一条可执行的规则**。
3. **`/skill-doctor`（见主线 8）是这条主线的诊断端**。

### 🎯 给本仓库的行动项

- **`CLAUDE.md` 412 行 vs 官方建议 ≤ 200 行**（超 106%）。
  建议按主线 5 的"分层"思路重写：
  - **常驻层（≤200 行）**：只留"这个仓库是干什么的 + 硬约束（验证命令、目录规范、提交格式）"；
  - **按需层**：把"插件架构详解""Error Playbook 说明""Git 提交规范"等移到独立 reference 文件，
    在需要时用 skill 或 Read 加载。
  验证方式：`/context` 看 CLAUDE.md 的字符占比（v2.0.74 起 `/context` 按来源分组）。
- **给本仓库的 6 个插件统一加 `experimental.cacheTtl: "1h"`**（v2.1.248）——
  本仓库的插件 agent 跑的是重复性的校验任务，5 分钟缓存基本等于没有缓存。
- **22 个能生效的项目级 skill 是本仓库自己贡献的 always-on 成本**。
  建议给不常用的几个（`taste-analyzer`、`design-scout`）加 `disable-model-invocation: true`，
  只在用户显式调用时载入 —— 这正是 `/skill-doctor` 会点名的那类 skill。

## 主线 6 · 插件生态：从「装个插件」到「有市场的插件」

### 现象

插件从一个"打包分发"功能，走成了一套**有依赖解析、有相关性推荐、有 eval 评分、有发布渠道**的生态。

### 证据

| 版本 | 变更条目 | 生态能力 |
|---|---|---|
| `v2.0.12`（2025-10-09） | `**Plugin System Released**: Extend Claude Code with custom commands, agents, hooks, and MCP servers from marketplaces` | 分发 |
| `v2.0.70`（2025-12-15） | `Added auto-update toggle for plugin marketplaces, allowing per-marketplace control over automatic updates` | 运维 |
| `v2.0.73`（2025-12-18） | `Added search filtering to the plugin discover screen (type to filter by name, description, or marketplace)` | 发现 |
| `v2.1.116`（2026-04-20） | `` `/reload-plugins` and background plugin auto-update now auto-install missing plugin dependencies from marketplaces you've already added `` | **依赖解析** |
| `v2.1.121`（2026-04-27） | `Added `claude plugin prune` to remove orphaned auto-installed plugin dependencies; `plugin uninstall --prune` cascades` | 依赖回收 |
| `v2.1.129`（2026-05-05） | `Added `--plugin-url <url>` flag to fetch a plugin `.zip` archive from a URL for the current session` | **托管分发** |
| `v2.1.154`（2026-05-28） | `The `/plugin` Discover tab now pins plugins whose relevance signals match the current directory with a "suggested for this directory" annotation` | **相关性推荐** |
| `v2.1.269`（2026-09-11） | `Added `claude plugin eval`: run a plugin's eval suite against Claude Code and get scored, reproducible results (JSON + HTML report); see `claude plugin eval --help`` | **质量评分** |
| `v2.1.286`（2026-09-30） | `Changed plugin installs to refuse npm sources that are git repositories or folders, and to install plugin dependencies only from registry packages` | 包源收敛到 registry |

`claude plugin eval` 的细节值得单独看：

- `v2.1.283`（2026-09-25）：`Changed `claude plugin eval` to require git 2.31 or later when git is installed`
- `v2.1.293`（2026-10-07）：`Fixed `claude plugin eval` refusing every Bash-granting run on Macs with Docker Desktop`
- `v2.1.299`（2026-10-14）：`Fixed `claude plugin eval` passing runs that the API refused: a run that ends on an API error now scores 0 without grading and makes the suite exit 1`

**最后一条尤其重要**：eval 在 API 报错时会**判 0 分并让套件 exit 1**。
这意味着 eval 可以直接当 CI 门禁用 —— 但也意味着**模型网关不稳定会误判 CI 失败**（本仓库用 `glm-4.7` 网关，风险实在）。

### 对使用者的含义

1. **生态有"包管理器"了**：依赖声明（v2.1.116）、依赖回收（v2.1.121）、包源收敛（v2.1.286）。
2. **生态有"质量门"了**：`claude plugin eval`（v2.1.269）是第一个**可复现、可打分**的插件质量指标。
3. **生态有"推荐算法"了**：relevance signals（v2.1.154）意味着平台开始按你的项目目录猜你要什么 ——
   **插件的竞争从"上架"变成"被推"**。

### 🎯 给本仓库的行动项

- **`.claude-plugin/marketplace.json` + 6 个插件的 manifest 就是本仓库的"产品目录"**。
  建议补齐生态化的三件事：
  1. **依赖声明**：若 `slidev-generator` 依赖别的插件，用 v2.1.116 的依赖字段显式声明；
  2. **相关性信号**：v2.1.154 靠目录匹配做推荐 —— 给每个插件的 `description` 补上**领域关键词**（本仓库的插件是进化生物学/作物育种/进化生态学），让 `/plugin` Discover 能把它们推给对的人；
  3. **eval 套件**：给每个插件写 `eval` case，让 `claude plugin eval` 能给出分数。
- **在 `.github/workflows/plugin-validation.yml` 里加一步 `claude plugin eval`**，
  但**必须处理 API 失败与"模型不合格"的区分**（v2.1.299 的 0 分语义）：
  建议 CI 里把 eval 的失败拆成两个 job —— "API/环境失败"重试，"分数不达标"才阻断。
  本仓库用 `glm-4.7` 网关，网关抖动会直接变成 0 分。
- **`--plugin-url`（v2.1.129）让"CI 拉本仓库的 marketplace zip 来测"成为可能**，
  这是本仓库最省事的分发方式 —— 不必发布到任何公开 marketplace。

### 对使用者的含义

1. **`/skill-doctor`（v2.1.261）把"skill 太多"从直觉变成了报告**：
   哪些 skill 没被用过、各占多少上下文 —— 第 02 章量化的 46,109 字符，现在有官方工具直接点名。
2. **OpenTelemetry 从"业务指标"扩展到"决策审计"**：
   `tool_decision` 带 `classifier_verdict`（v2.1.301）、`claude_code.safety_event`（v2.1.307）——
   **每一次被拦下的工具调用都是一个可观测事件**。
3. **但 v2.1.312 又把 `claude_code.safety_event` 停掉了**（`Changed Claude Code to stop sending the claude_code.safety_event OpenTelemetry event`）——
   **可观测性字段本身也在变**，写告警规则时别把字段名写死。

### 🎯 给本仓库的行动项

- **本仓库有三个现成但没用的诊断入口**：
  1. `/skill-doctor`（v2.1.261）—— 直接回答"23 个项目级 skill 里哪些是白交的学费"；
  2. `/context`（v1.0.86 / v2.0.74）—— 回答"CLAUDE.md 412 行到底占了多少"；
  3. `--debug-file`（v1.0.123 / v2.1.280）—— 回答"为什么某个插件没加载"。
  **建议把这三条写进 `docs/cc-guide/07-排错手册.md` 的速查表**，并在 `.claude/hooks/check-skills-limit.sh` 里接上。
- **`/skill-doctor` + `check-skills-limit.sh` 可以合成一条 CI 门禁**：
  本仓库已有 `scripts/measure_context.py` 做同样的事，
  建议把"skill 总 description 字符数 > 阈值"加成 CI 检查，
  超过就提醒而不是硬失败（`/usage` 的 always-on context 告警就是这个思路，v2.1.299）。
- **OpenTelemetry 建议只开 `tool_decision` 一类事件**，别全开：
  `OTEL_LOG_TOOL_DETAILS=1` 才会带 `tool_parameters`（v2.1.85），
  而本仓库用模型网关，全量事件会把网关的 API key 之类的东西带进日志。
